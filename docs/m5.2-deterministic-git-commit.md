# M5.2 deterministic Git commit construction

M5.2 consumes the immutable M5.1 `GitEffectPlan` and creates a candidate Git
commit in MIRAGE-owned disposable storage. It does not make the commit
reachable and performs no real Git or network mutation.

## Authority flow

```text
RunManifest + contract + trusted clock
                  |
frozen final rescan + canonical diff
                  |
GitRepositoryBinding + GitEffectPlan revalidation
                  |
exact verified mutation bytes
                  |
transaction-only blob -> exact tree rewrite -> canonical commit
                  |
second full authority/frozen-state/repository revalidation
                  |
sealed CommitArtifact
```

Immediately before transaction creation, the lifecycle validates the manifest,
observes its rollback-protected trusted clock, checks contract expiry,
revalidates the M5.1 plan and repository binding, rescans the complete M4-visible
real baseline, and rescans the frozen disposable workspace. The new blob bytes
come only from the recomputed frozen-tree mutation. Its resource, operation,
kinds, modes, before/after digests, and bound base blob must exactly equal the
`GitEffectPlan` effect.

After construction, the lifecycle repeats the trusted-time, real repository,
frozen final tree, canonical diff, Git plan, and artifact checks. A concurrent
change leaves no usable artifact and transaction cleanup uncertainty dominates
a semantic conflict or rejection.

## Exact construction method

M5.2 deliberately does not create a transaction index and does not run `git
add`, `git commit`, `read-tree`, `write-tree`, or `update-index`. Instead:

1. bounded read-only `git cat-file` reads already-bound base tree objects from
   the real repository; M5.1 binding revalidation occurs on both sides of every
   read, commands have a ten-second timeout, lazy fetching is disabled, and the
   child environment remains an allowlist;
2. trusted Go code hashes the exact verified bytes as a raw SHA-1-format Git
   blob and writes the compressed loose object only under a protected
   `.mirage-m52-*` transaction root;
3. trusted Go code parses only the base-tree chain containing the canonical
   authorized path, replaces the exact M5.1 base blob OID, preserves every
   other entry byte-for-byte, and writes the resulting tree objects only to the
   transaction store;
4. trusted Go code serializes the commit object exactly as:

   ```text
   tree <new tree>
   parent <M5.1 base commit>
   author MIRAGE <mirage@localhost> <CreatedAt Unix seconds> +0000
   committer MIRAGE <mirage@localhost> <CreatedAt Unix seconds> +0000

   <M5.1 deterministic message>\n
   ```

   Nanoseconds are floored to whole Unix seconds. Author and committer times are
   identical. No host identity, encoding header, signature, or second parent is
   accepted.

The direct object implementation avoids worktree conversion, attributes,
clean filters, `autocrlf`, pathspec parsing, option parsing, hooks, ambient Git
configuration, and accidental index/ref updates. Tests independently ask Git
to parse the resulting commit and diff the base/new trees.

## Transaction and artifact

The protected transaction contains only `objects/<fanout>/<object>` paths. It
has no config, index, refs, worktree, alternates file, credentials, or remote.
Writes are derived from bounded M4 content and a bounded 64 MiB base-tree walk;
compressed transaction writes have an 80 MiB ceiling. The sandbox never sees
this host-side directory.

`CommitArtifact` binds:

- manifest, M5.1 plan, repository binding, and reconciliation identities;
- base commit/tree, target ref, resource, and base blob;
- new blob, new tree, constructed commit, and canonical Git timestamp;
- a canonical artifact identity that excludes the physical transaction path.

Revalidation verifies the physical transaction root/object-store identities,
the exact object set, loose-object hashes/types/sizes/bytes, the deterministic
tree rewrite, canonical commit bytes, and every upstream authority. Callers
receive immutable values only. One lifecycle returns the same retained artifact
on repetition and cannot mint another artifact after cleanup.

Selecting M5.2 permanently excludes the M4 direct real-file commit path for
that lifecycle. Explicit artifact cleanup, rejection, or lifecycle destruction
removes transaction state. A physical-root replacement or cleanup failure is
`FAILED` uncertainty and leaves evidence rather than deleting an unproven path.
The lifecycle retains a private cleanup-only capability in that case without
returning the failed artifact as usable commit authority.

## Exact guarantee and limitations

For the supported M5.2 topology, MIRAGE proves:

```text
constructed commit delta == one verified existing-file MODIFY
real worktree/index/HEAD/refs/reflogs/config/object database after == before
```

M5.2 still assumes the host, MIRAGE process, OS, temporary filesystem, and Git
binary used for bounded base-object reads are trusted. Protected host temporary
storage is logically size-bounded; this milestone does not provision a separate
filesystem quota for it. Repeated observation narrows but cannot make a hostile
host filesystem globally atomic.

M5.2 does not write real objects, create/update refs or branches, fetch, push,
contact GitHub, use credentials, provide crash-durable publication, widen beyond
one existing regular-file content modification, or issue receipts. Exact
publication of this already-proven artifact is deferred to M5.3.
