# M5.4 GitHub pull-request effect design

> **Status:** Design proposal only. No M5.4 mutation code is authorized by this
> document.

M5.4 extends the closed M5.3 boundary by establishing one exact pull request
for one authoritatively published MIRAGE branch. It does not merge, edit, close,
reopen, label, comment on, review, or delete anything on GitHub.

The external effects are deliberately not presented as one atomic transaction:

```text
CREATE_BRANCH succeeds permanently
        |
        v
CREATE_PULL_REQUEST is absent, established, conflicting, or uncertain
        |
        v
MIRAGE preserves both facts independently
```

The governing invariant is:

```text
CommittedExternalEffects subset-of AuthorizedExternalEffects
```

## Scope

Version 0 supports exactly:

- one M5.3 `PublicationRecord` that authoritatively proves an exact
  `TargetRef -> CommitOID` in one bound github.com repository; and
- one `CREATE_PULL_REQUEST` effect from that exact head to the exact bound
  `BaseRef`.

The base ref must still point to M5.3's bound `BaseCommit` immediately before
PR creation. This deliberately rejects a PR whose comparison base changed after
the run was authorized.

M5.4 does not support arbitrary bases or heads, forks, draft PRs, metadata
chosen by the model or repository, PR updates, retries after an uncertain POST,
branch updates or deletion, compensation, GitHub Enterprise, generic GitHub
mutation, or any widening of the M4.3 one-existing-file commit boundary.

## Trust boundary

The agent, model, prompts, repository contents, sandbox process, arbitrary URLs,
suggested refs, suggested PR text, ambient Git configuration, ambient GitHub CLI
authentication, and ambient credentials are untrusted.

The lifecycle, contract evaluator, immutable bindings and plans, narrow GitHub
client, host-only credential source, authoritative observations, and immutable
effect records are trusted.

These paths remain forbidden:

```text
agent              -> GitHub API
model              -> GitHub authority decision
CommitArtifact     -> PR creation
PublicationRecord  -> PR creation
PR plan possession -> PR creation
```

Only a trusted lifecycle transition may dispatch the external mutation, after
freshly revalidating every upstream authority at the last possible point.

## Contract decision: deliberate v3

M5.4 should introduce `mirage.contract/v3`. A compatible extension of v2 is
rejected because v2's canonical schema and security meaning authorize exactly
one `CREATE_BRANCH` policy. Silently adding a PR field or changing evaluation
would make the same version string represent different authority.

The implementation must retain the existing dedicated v1 and v2 canonical
structures unchanged. Their JSON bytes, golden hashes, validation, and default
denials must remain byte-for-byte compatible. V1 and v2 always deny
`CREATE_PULL_REQUEST`.

V3 contains the existing filesystem policy plus two explicit GitHub effect
policies:

```text
github:
  repository_full_name: <canonical lower-case owner/repo>
  branch:
    operation: CREATE_BRANCH
    target_ref: refs/heads/mirage/run-<deterministic suffix>
  pull_request:
    operation: CREATE_PULL_REQUEST
    base_ref: refs/heads/<exact trusted base>
    head_ref: <same exact target_ref>
    metadata_policy: mirage.pr-metadata/v1
```

The v3 evaluator authorizes only an exact tuple:

```text
CREATE_PULL_REQUEST(
  repository_full_name,
  BaseRef,
  TargetRef,
  mirage.pr-metadata/v1,
)
```

V3 must continue to authorize M5.3 branch creation through its exact branch
sub-policy so one immutable run contract binds both irreversible effects. M5.3
plan validation may accept v2 or v3 only after evaluating the corresponding
exact `CREATE_BRANCH` authority; it must not infer authority merely from the
contract version.

Before implementation, tests must pin the current v1/v2 canonical encodings
and hashes, then add independent v3 canonical-ordering, duplicate-field,
unknown-operation, malformed-ref, and default-deny coverage.

## Deterministic PR metadata

`mirage.pr-metadata/v1` owns all authority-bearing text. Raw model output,
repository prose, environment values, URLs, commit messages, and arbitrary
user-supplied Markdown are excluded.

The title is fixed-format ASCII:

```text
MIRAGE verified change <12 lowercase hex characters from the run identity>
```

The body is a fixed-order, bounded template containing only canonical trusted
data:

- run identity digest, not raw agent prose;
- contract identity;
- exact verified mutation kind and canonical workspace resource;
- `CommitOID`;
- `PublicationRecord` identity; and
- a fixed statement that MIRAGE shadow-executed and verified the change.

The initial boundary permits at most 120 UTF-8 bytes for the title and 4 KiB
for the body. Generated content must be valid UTF-8, contain no control
characters other than template newlines, and be produced identically from the
same structured input. The plan binds the exact title, exact body, metadata
policy version, and their SHA-256 digests.

The body is GitHub Markdown, so dynamic fields are never interpolated as raw
Markdown. The metadata policy renders digests and numeric identities in their
fixed canonical alphabets. It renders a canonical workspace resource as
unpadded base64url of its UTF-8 bytes inside a fixed inline-code field, together
with its SHA-256 digest. The encoded alphabet cannot terminate the code span or
introduce a GitHub mention, link, HTML tag, Markdown delimiter, or line break.
Encoding and size validation happen in trusted deterministic code; neither the
agent nor GitHub rendering supplies escaping semantics.

## Immutable `GitHubPullRequestPlan`

The plan is derivable only after the M5.3 publication record freshly proves the
exact remote branch. Its canonical identity binds:

- plan version;
- manifest hash and contract hash;
- local repository binding identity;
- Git plan identity;
- `CommitArtifact` identity;
- `GitPublicationPlan` identity;
- `PublicationRecord` identity;
- GitHub repository-binding identity;
- repository stable numeric ID and canonical full name;
- exact `BaseRef` and bound `BaseCommit`;
- exact `TargetRef` and `CommitOID`;
- operation `CREATE_PULL_REQUEST`;
- metadata-policy version;
- exact title and body plus their digests;
- trusted creation time; and
- canonical plan identity/hash.

It contains no credential, URL, agent/model text, ambient configuration,
filesystem transaction path, or mutable client. Repeated derivation returns the
same immutable plan only after fresh validation; it must not consume another
trusted timestamp or produce a different identity.

The plan is data, not a capability. The narrow GitHub client must not accept it
directly from arbitrary callers as sufficient authority.

## Exact preconditions and dispatch authority

Before any POST, trusted code proves, in order:

1. the lifecycle is in the exact post-M5.3 state and has no prior PR mutation
   attempt;
2. trusted time has not rolled back and the contract is not expired;
3. the manifest and contract identities are unchanged;
4. the local repository binding, Git plan, and `CommitArtifact` are valid;
5. the `GitPublicationPlan` and `PublicationRecord` are valid and mutually
   bound;
6. the GitHub repository stable ID and full name are unchanged;
7. `BaseRef -> BaseCommit` still holds;
8. `TargetRef -> CommitOID` still holds;
9. the exact v3 PR policy evaluates allowed;
10. the immutable PR plan recomputes to the same identity; and
11. exact-PR preflight has an authoritative classification.

If preflight is `ABSENT`, the lifecycle invokes one mandatory authority
callback immediately before constructing/dispatching the HTTP POST. That
callback repeats trusted-time, manifest, every upstream identity, both exact
remote refs, the v3 decision, the PR-plan identity, credential availability,
and the no-prior-attempt condition.

Any observed change is `CONFLICTED`. Inability to establish current state is a
structured failure or uncertainty as described below and performs no new
mutation. Clock rollback, expiry, malformed evidence, or missing credentials
fail closed with zero POST attempts.

## One-way `PullRequestAttempt` latch

The exact mutation ordering is:

```text
preflight = ABSENT
  -> construct and validate the exact canonical request bytes
  -> final lifecycle authority callback
  -> mint immutable PullRequestAttempt
  -> install attempted=true and transition to PR_CREATING
  -> enter HTTP transport exactly once
  -> authoritative postflight
```

Installing the attempt and entering `PR_CREATING` is a one-way in-memory latch
and occurs before control enters the HTTP transport. It is never cleared by a
timeout, 4xx/5xx status, malformed acknowledgement, caller cancellation,
response parse failure, reconciliation failure, or cleanup failure. Once the
latch is installed, every later lifecycle operation is read-only
reconciliation. No semantic or cleanup outcome can make another POST legal in
that lifecycle instance.

The minimal immutable `PullRequestAttempt` binds:

- PR-plan identity;
- repository stable numeric ID;
- exact `BaseRef`, `TargetRef`, and `CommitOID`;
- SHA-256 digest of the complete canonical request representation;
- exact title and body digests;
- trusted final-authority/dispatch time; and
- canonical attempt identity.

It contains no credential, client, URL, raw header, or mutable state. The
attempt record and latch are installed together while the lifecycle owns its
transition lock; failure to install either means the HTTP transport is not
entered. This is intentionally a narrow lifecycle record, not a general
workflow abstraction.

The latch is not crash-durable in M5.4 v0. At-most-once dispatch is therefore
guaranteed only within one uninterrupted lifecycle instance. If the process is
lost after dispatch may have begun, that run cannot resume external mutation in
v0. Cross-restart at-most-once behavior requires durable pre-dispatch attempt
recording and recovery and remains deferred.

## Narrow GitHub client

The M5.4 client exposes only two semantic operations:

```text
ObserveExactPullRequest(repository ID/name, base ref, head ref, head OID,
                        metadata identity)
CreateExactPullRequest(repository ID/name, base ref, head ref,
                       exact title/body, draft=false)
```

It is not a generic request method. The implementation fixes
`https://api.github.com`, disables proxy discovery and redirects, rejects
cross-origin behavior, uses explicit connect/TLS/header/overall timeouts,
bounds request and response bodies, and semantically validates every status and
JSON field used for security decisions. Reads use bounded pagination or a
strict result cap and query all PR states so a closed historical PR is not
silently ignored. If enumeration reaches the result/page cap before proving
completion, or any required page cannot be obtained and validated, the result
is `UNAVAILABLE`, never `ABSENT`.

Internal refs remain canonical full refs. Trusted deterministic conversion
accepts only `refs/heads/<validated branch>` and mechanically produces the
GitHub API's base branch name and same-repository `owner:head-branch` query
form. API strings never choose repository or head semantics. Responses must
map back to the exact internal `BaseRef` and `TargetRef`, and both base and head
repository IDs must equal the bound repository ID; a fork is always a conflict.

An exact observation validates repository ID, base repository and ref, base
SHA, head repository and ref, head SHA, draft/state, title, body, PR number,
stable PR identity, and the canonical GitHub URL origin. `PRESENT_EXACT`
requires both `BaseRef == authorized BaseRef` and
`BaseSHA == bound BaseCommit`, together with
`TargetRef == authorized TargetRef` and `HeadSHA == CommitOID`. This does not
make GitHub's query/create operation atomic; it refuses to certify a PR whose
base authority changed in the final observation/POST window.
Provider-preserved owner/repository display casing in `html_url` is validated
semantically against the canonical repository authority, after which MIRAGE
constructs and binds its own lowercase canonical URL; encoded or otherwise
ambiguous path spellings are rejected. Fork heads are conflicts. More than one
candidate, a closed PR, a draft PR, or matching refs with different
authority-bearing metadata is `PRESENT_CONFLICTING`, not exact.

The dedicated token remains host-only and is sourced explicitly. It never
appears in argv, URLs, redirects, logs, errors, plans, records, PR metadata,
sandbox/container state, model context, broker traffic, workspace data, or
ambient Git/GitHub CLI configuration. Raw HTTP request/response dumps are
forbidden. Diagnostics expose only bounded, redacted stage/status categories.

There is no automatic POST retry at any layer. Within an uninterrupted
lifecycle, the attempt latch makes a second POST structurally unavailable.
Read-only observation may be repeated for reconciliation.

## Idempotency and the query/create race

Preflight classifies the exact repository/base/head tuple:

```text
ABSENT
  -> eligible for exactly one POST

PRESENT_EXACT
  -> zero POSTs
  -> desired state is already established
  -> causality is PREEXISTING unless an existing MIRAGE record proves otherwise

PRESENT_CONFLICTING
  -> CONFLICTED, zero POSTs

UNAVAILABLE
  -> fail closed before mutation
```

GitHub does not provide an atomic compare-and-create PR primitive. A PR may
appear after `ABSENT` but before MIRAGE's POST. MIRAGE still sends at most one
POST and always performs a postflight read, including after a 4xx response,
timeout, connection reset, malformed acknowledgement, or cancellation.

The postflight authoritative observation, not the transport result, determines
the proven state:

```text
PRESENT_EXACT       -> desired PR state established
PRESENT_CONFLICTING -> CONFLICTED
ABSENT              -> NOT_CREATED / FAILED
UNAVAILABLE         -> PR_CREATION_UNCERTAIN
```

An exact PR found after a lost acknowledgement proves the desired state, but
does not prove that MIRAGE exclusively caused it. The record preserves
`transport_acknowledged` and causality separately. MIRAGE never issues a second
POST within the uninterrupted lifecycle. A later call in
`PR_CREATION_UNCERTAIN` may perform read-only reconciliation only.

After the attempt latch is set, postflight and later reconciliation use a fresh
trusted bounded context rather than reusing the caller's possibly cancelled
context. The reconciliation context has its own fixed timeout/body/page bounds
and remains subject to trusted runtime shutdown. Caller cancellation may stop
waiting for the result, but cannot convert a required reconciliation read into
permission for another mutation.

## Lifecycle and truthful partial effects

Three M5.4-specific lifecycle concepts are sufficient:

```text
PUBLISHED
  -> PR_CREATING
  -> PR_ESTABLISHED | FAILED | CONFLICTED | PR_CREATION_UNCERTAIN

PR_CREATION_UNCERTAIN
  -> PR_ESTABLISHED | FAILED | CONFLICTED | PR_CREATION_UNCERTAIN
     (read-only reconciliation only)
```

`PR_ESTABLISHED` means the exact desired PR exists. It does not by itself claim
MIRAGE created the PR; the effect record carries that evidence. Existing
`FAILED` and `CONFLICTED` states are retained, but consumers must consult the
external-effect ledger, which still proves the branch is permanently
published. No state transition erases an established external fact.

The immutable `ExternalEffectLedger` binds the run, manifest, contract, all
upstream plan/record identities, and two independently versioned entries:

```text
BranchEffect:
  operation: CREATE_BRANCH
  outcome: PUBLISHED
  ref: TargetRef
  oid: CommitOID
  publication_record_identity: ...

PullRequestEffect:
  operation: CREATE_PULL_REQUEST
  outcome: NOT_ATTEMPTED | NOT_CREATED | ALREADY_PRESENT | CREATED | CONFLICTED | UNCERTAIN
  attempted: false | true
  repository_id: ...
  base_ref: ...
  base_commit: ...
  head_ref: ...
  head_oid: ...
  metadata_policy: ...
  title_digest: ...
  body_digest: ...
  number: required when established
  stable_id: required when established
  url: required validated github.com URL when established
  plan_identity: ...
  attempt_identity: optional
  transport_acknowledged: false | true
  exact_postflight: false | true
  reconciled: false | true
  causality: NONE | PREEXISTING | MIRAGE_ACKNOWLEDGED | UNKNOWN
```

Each update creates a new canonical ledger snapshot linked to the preceding
identity; it never rewrites or downgrades the branch fact. `CREATED` requires
both exact postflight state and an acknowledged compatible create response.
Lost acknowledgement plus exact postflight state is `ALREADY_PRESENT` with
`UNKNOWN` causality, not an unsupported claim of exclusive creation.

Outcome-specific canonical validation rejects impossible snapshots:

- for every outcome, `attempted=true` if and only if an attempt identity is
  present; `attempted=false` forbids transport acknowledgement;
- `NOT_ATTEMPTED` requires `attempted=false`, no attempt identity, no transport
  acknowledgement, and no established PR identity;
- `NOT_CREATED` requires `attempted=true`, an attempt identity, and an
  authoritative postflight observation of `ABSENT`;
- `CREATED` requires `attempted=true`, an attempt identity, an exact
  postflight, a compatible acknowledged create response, and causality
  `MIRAGE_ACKNOWLEDGED`;
- `ALREADY_PRESENT` requires an exact authoritative observation. A preflight
  exact result has `attempted=false`, no attempt identity, and causality
  `PREEXISTING`; a post-attempt exact result without a compatible acknowledged
  create response has `attempted=true`, retains its attempt identity, and uses
  causality `UNKNOWN`;
- `CREATED` and `ALREADY_PRESENT` require the exact PR number, stable GitHub PR
  ID, validated github.com URL, repository ID, `BaseRef`, `BaseCommit`,
  `TargetRef`, head `CommitOID`, metadata policy, and exact title/body digests;
- `UNCERTAIN` requires `attempted=true`, the attempt identity, and unavailable
  authoritative postflight; it may omit external PR identity because no exact
  PR was established;
- `CONFLICTED` binds the bounded non-secret conflicting observation evidence
  available without representing it as the authorized PR, and retains an
  attempt identity exactly when the conflict was observed after dispatch; and

Thus a missing token or failed precondition is `NOT_ATTEMPTED`, while a POST
followed by authoritative absence is `NOT_CREATED`. Those security facts can
never share a canonical representation.

M5.4 performs no compensating branch deletion when the PR fails or is
uncertain. External effects are not crash-atomically grouped.

## Proposed trusted authority surfaces

Implementation should add only these narrow surfaces:

- contract-v3 construction and exact PR evaluation;
- deterministic PR metadata construction;
- immutable PR-plan derivation/revalidation;
- exact read-only PR observation;
- one lifecycle-only PR creation dispatch;
- read-only uncertain-result reconciliation; and
- immutable partial-effect ledger construction.

No exported package function may create a PR without the lifecycle's final
authority callback. No generic GitHub mutation interface is introduced.

## Deterministic and adversarial test gate

Before live use or hostile review, tests must prove at least:

1. exact published branch and absent PR causes one POST and one exact PR;
2. missing branch causes zero POSTs;
3. a different target OID causes zero POSTs;
4. moved base causes zero POSTs and conflict;
5. changed repository ID causes zero POSTs;
6. an exact existing PR causes zero duplicate POSTs;
7. a conflicting, closed, draft, fork, or duplicate candidate conflicts;
8. a PR appearing between preflight and POST is classified only by postflight;
9. acknowledged creation plus exact postflight becomes `CREATED`;
10. lost acknowledgement plus exact postflight becomes established without a
    retry or false causality claim;
11. failed POST plus authoritative absence becomes `NOT_CREATED`;
12. unavailable postflight becomes `UNCERTAIN`, and every subsequent operation
    is read-only;
13. expiry before final authority causes zero POSTs;
14. trusted-clock rollback fails closed;
15. stale publication plan or record causes zero POSTs;
16. title/body and every plan/record/ledger identity are deterministic;
17. raw model, agent, repository, environment, and URL text cannot enter PR
    authority or metadata;
18. absent credentials cause zero POSTs;
19. credential leak inventory is empty;
20. cleanup uncertainty is not mislabeled as a semantic outcome;
21. v1/v2 golden canonical bytes and hashes remain unchanged; and
22. all M1-M5.3 vet/race/coverage and applicable rootless hostile, broker, and
    leak suites remain green.

The suite must also prove that the attempt latch is installed before the test
transport observes the POST; every transport/error/cancellation path retains
it; concurrent callers cannot dispatch twice; every post-attempt invocation is
read-only; `NOT_ATTEMPTED` and `NOT_CREATED` cannot be interchanged; established
outcomes cannot be built without exact PR identity; cancelled caller context
does not suppress the fresh bounded postflight; ref conversion rejects
non-head/fork/ambiguous forms; and truncated enumeration is `UNAVAILABLE`.

Mocks/fakes are preferred for deterministic authority and failure coverage.
No test should spend provider or GitHub quota when a fake can prove the same
property.

### Local model testing

The locally installed Qwen model may be used when it materially adds evidence
for the sandboxed coding-agent or broker path. Before use, tests detect the
configured local runtime/model; they do not download another model or silently
fall back to a hosted provider. An explicitly model-dependent test skips or
fails cleanly when unavailable and reports whether it used the real local model
or a fake.

The local model remains untrusted input behind the existing sandbox/broker
boundary. It receives no GitHub token, host credential, real-repository secret,
or unrestricted network access. It never decides contract authorization, final
verification, commit authority, branch publication authority, PR authority,
conflict classification, or uncertain-result reconciliation. M5.4 PR
authorization is completely model-independent.

## Live proof gate

No live M5.4 GitHub proof occurs until deterministic hostile review approves
the implementation. A later live test uses only `MrGray17/test` or another
explicit disposable repository and may create exactly one M5.3 MIRAGE branch
and one exact PR into the bound base. It performs no merge, comment, label,
review request, close, cleanup, branch deletion, or second POST after
uncertainty.

## Exact guarantee and remaining limitations

For the proposed v0 state model, one uninterrupted M5.4 lifecycle instance will
dispatch at most one PR-create request, only for the exact contract-authorized
repository, published head, stable head commit, unchanged base, and
deterministic metadata, after fresh lifecycle authority and installation of
the one-way attempt latch. It then records independently what is proven about
the already-published branch and the PR.

M5.4 cannot make GitHub's query/POST sequence atomic, prove exclusive causality
after a lost acknowledgement, undo an established branch, prevent a GitHub
administrator from changing remote state after observation, or guarantee
availability. GitHub, DNS/TLS trust, the host OS/runtime, the Go HTTP stack, and
the dedicated host credential remain trusted. The v0 attempt latch and effect
ledger are not crash-durable. A run whose process is lost after PR dispatch may
have begun is not eligible to resume external mutation; the global guarantee
does not claim one POST across process restart. Durable pre-dispatch recording,
restart reconciliation, and cross-restart at-most-once semantics remain
deferred together with signed receipts, automatic compensation, PR
modification, and generalized GitHub automation.
